Build a Sepolia attack demo: a stolen Safe owner key tries to send USDC; Newton passkey checks deny it and the UI shows that the protocol protected the funds.

Product The thing people see is an attack demo, not a passkey-registration app and not a Vercel deploy. Headline: This key used to be able to empty the Safe. Now it can’t without a passkey. The page signs with the published throwaway Safe owner key (`NEXT_PUBLIC_COMPROMISED_PRIVATE_KEY`; displayed on the attack screen), enters a recipient and an amount, and submits Sepolia USDC (0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238, 6 decimals) with the stolen key and without a valid tap. Newton must deny. The UI then shows a clear protected state (green or equivalent): passkey validation failed, you were protected by the Newton protocol, here is the link to the task evaluation. A legitimate send with a fresh valid tap can still succeed so we can contrast allow vs deny; that is not the story on the page. That tap only works on this machine (this origin and this authenticator), never on a hosted UI. Honey-pot USDC lives on a Safe. The compromised key is a Safe owner. A Safe Guard blocks every owner execTransaction, so a raw Safe send, setGuard(0), or disableModule from that key cannot drain the pot. The only remaining spend path is the Newton PolicyClient module. intent.from is the published owner EOA and must equal msg.sender. Do not use a relayer. Passkey registration is local setup only (once, for secrets upload). Never ship a registration product, never put registration on Vercel, never deploy this UI to Vercel.

Policy

Allow a transfer(address recipient, uint256 amount, bytes32 tapNonce) when amount <= 10 USDC (10000000 base units) and the data WASM verifies a WebAuthn assertion for this tap.
Deny over the cap, a bad/wrong-key assertion, or a challenge that does not match this intent.
Cap is a policy parameter I can change later (maxAmount).
WASM is not a stub. Spike re-run on newton-cli 0.5.2 (same crypto result as 0.4.21): a full P-256 ECDSA verify will not run under policy simulate. crypto.subtle componentizes but calls WASI random (disabled by policy build). Noble Point.add / multiplyUnsafe trap even for 2·G. SHA-256, Point.fromBytes, toAffine, and Fp.mul/inv do run. Affine double allows at 32 and 48 rounds and traps at 64+ (fuel); one P-256 scalar mul needs ~256 doubles, verify needs two. Do not retry in-component P-256. 0.5.2 injects oracle JSON at data.wasm.* (not data.data.*) and local simulate no longer needs a newton-cli.toml.
WASM may parse the assertion, SHA-256 clientDataJSON, and check challenge / origin / rpIdHash / flags against secrets. Do not implement P-256 in policy.js. POST the assertion to https://demo-passkey-verifier.vercel.app/api/verify over newton:provider/http for both local simulate and live evaluate. Optional verifier API key lives in Newton secrets if VERIFIER_API_KEY is set on that service. Do not build, vendor, or deploy the verifier in this demo. Do not use localhost and do not invent a different host.
Passkey public key, credentialId, and expected rpId/origin live in Newton secrets (getSecrets()), never in wasm_args. The assertion (authenticatorData, clientDataJSON, signature) is wasm_args only.
WebAuthn challenge must be hash(intent including tapNonce), not hash(intent) without the nonce. Duplicate transfers to the same recipient are allowed; each send needs a new tap and a new tapNonce. Do not one-shot the intent. Do not treat signCount as consumption. WASM only returns success plus the challenge/tapNonce it verified; it does not consume anything.
Chain: Ethereum Sepolia (11155111). Intent value is 0. The intent target is the USDC token, not the wrapper.

App contract Wrap the transfer in a Newton PolicyClient enabled as a Safe module. After a successful attestation, move USDC from the Safe with execTransactionFromModule → USDC.transfer(recipient, amount). Do not transferFrom the compromised key. Do not approve that key or the PolicyClient on the Safe's USDC.
Set a Safe Guard that reverts every owner execTransaction. Safe 1.4.1 does not run the Guard on execTransactionFromModule. Add the compromised key as a Safe owner and set the Guard in the same Safe transaction (MultiSend) so there is no window where that key can drain. After the Guard is on, owners cannot unset it or disable the module via execTransaction.
Use _validateAttestationDirect as-is for task replay (taskId spend). Do not add a second task-id map and do not consume taps inside the mixin.
Consume the tap in PolicyClient storage, keyed by tapNonce decoded from the attested intent (not from wasm_args or extra unattested calldata): require unused, then mark used, in the same tx as the transfer. Reusing a tapNonce reverts. A failed transfer must not keep the nonce spent (same-tx revert is enough).
Do not add an intent nonce that blocks a second honest 10 USDC to the same recipient.

Frontend A local Next.js page is enough. The main screen is the compromised-owner attack: headline that this key used to be able to empty the Safe and now cannot without a passkey, recipient, amount, evaluate/submit without a valid assertion (or with a deliberately bad one). No token approve CTA. On deny, show the protected banner and a link to the Newton task evaluation. Do not make passkey registration the product UI; if a one-time local register helper is needed so I can upload secrets, keep it off the demo story (setup only). Keep the Newton API key off the browser (server Route Handler only; never NEXT_PUBLIC_*). A scraped gateway key can evaluate tasks and upload dashboard secrets as the PolicyClient owner. Do not deploy to Vercel.
