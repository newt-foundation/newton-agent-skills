# Deploy, secrets, and live evaluate reference

Use only after local allow/deny simulation passes and the user explicitly asks
to deploy or run live evaluation.

## Disclose early; collect at the deployment checkpoint

When live deployment is requested, state at the beginning that deployment will
eventually need:

- A funded local `PRIVATE_KEY` (process environment or `~/.newton/.env`)
- A Newton gateway API key from `newton-cli keys` (secrets / live evaluate)
- `CHAIN_ID`
- `RPC_URL`. Ethereum Sepolia (`11155111`) defaults to the public endpoint
  `https://ethereum-sepolia-rpc.publicnode.com`. Do not ask the user for a
  Sepolia URL. Prefer an already-set `RPC_URL`. If that public endpoint
  rate-limits, ask them to inject their own URL outside chat.
- An IPFS route:
  - Newton proxy: default; no Pinata credentials
  - Direct Pinata: both `PINATA_JWT` and `PINATA_GATEWAY`

Also name where those secrets should live: the process environment or
`~/.newton/.env` (the durable location both the CLI and this skill load). Do
not ask for values, do not create or populate `~/.newton/.env` for the user,
and do not tell them to do this at install, `doctor`, login, or scaffold.

Do not ask the user to provide these values in chat and do not require them for
scaffold/build/local simulation. Continue through local allow/deny validation.

After local simulation passes and before the first upload or transaction:

1. Read `<policy-dir>/configs/deployment.toml`, generated by `policy scaffold`,
   for non-secret defaults such as chain ID and expiration. Read
   `<policy-dir>/.env.example` only as a checklist of supported variables.
2. Reuse values already available from explicit user input, the real process
   environment, or `~/.newton/.env`. Do not search other files.
3. Identify only the missing requirements. Verify secret-bearing environment
   variables by presence without printing their values.
4. If `PRIVATE_KEY` or (when using direct Pinata) `PINATA_JWT` /
   `PINATA_GATEWAY` are missing from both the process environment and
   `~/.newton/.env`, **stop**. Ask the user to inject them outside chat into
   the process environment or `~/.newton/.env`. Resume only after a presence
   check succeeds. If `RPC_URL` is unset and the target is Ethereum Sepolia
   (`11155111`), use `https://ethereum-sepolia-rpc.publicnode.com` for this
   session. If `RPC_URL` is unset on any other chain, **stop** and ask the
   user to inject it the same way. A credential-bearing RPC (API key in the
   URL) is still a secret; never print it.
5. Ask for non-secret choices such as chain/environment and IPFS route when
   they cannot be inferred.
6. Summarize the target chain, planned uploads, and transactions, then obtain
   explicit deployment confirmation.

Do not source or read:

- A project-local `.env` (including the policy directory)
- A `.env` beside a user-specified `newton-cli` binary
- Another repo checkout
- Shell rc files (`~/.zshrc`, `~/.zprofile`, and similar)

A custom CLI path does not change this lookup. An empty `~/.newton/.env` is
missing credentials, not a source to use.

Never invent private keys, credential-bearing RPC URLs, contract addresses,
chain IDs, or expiration values. The public Sepolia RPC above is the allowed
exception when `RPC_URL` is unset on `11155111`. Do not print or commit
credentials. Login/API-key setup is required for gateway operations such as
secrets/live evaluate, but not inherently for scaffold/build/local simulation
or Newton-proxy IPFS upload.

Policy lifecycle commands do not require the legacy full
`~/.newton/newton-cli.toml`. With `-p <policy-dir>`, `policy deploy`
automatically reads `configs/deployment.toml`; CLI/environment values override
the file. Use `--deployment-config <path>` only when selecting another
non-secret profile.

Policy-client wiring has additional just-in-time inputs:

- PolicyClientRegistry address
- Existing policy-client contract address
- Expiration values

The application contract must already implement `INewtonPolicyClient`. This
skill wires an existing client; it does not implement or deploy the user's
application contract. Use `newton-policy-client` to create that contract,
bind attested intents, deploy the client with the local key, `setPolicies`
(ordered set of 1–8 Policies), and transfer `setPolicyClientOwner` to the
`newton-cli login` wallet before secrets.

## End-to-end order

```text
build
  → if published: policy packs show --format json (policy address, not PolicyData)
  → one policy deploy -p per policy (wasmCid on that Policy; empty for pure Rego)
  → newton-policy-client: deploy / setPolicies (1–8, ordered) / register / setPolicyClientOwner(login wallet) via cast
  → upload secrets when used (requires getOwner() == login wallet; once per Policy that calls getSecrets())
  → optional live evaluate (EIP-712 sign + gateway newt_createTask)
```

## Orchestrated deploy

### One Policy per directory

```bash
newton-cli policy deploy -p <policy-dir>
```

Run this once per policy. It generates CIDs and deploys one Policy. The
Policy's `wasmCid` is that directory's WASM, or empty for pure Rego. It does
not deploy a separate PolicyData contract and it does not take a PolicyData
address. Do not pass `--policy-data-address`.

It resolves `RPC_URL` and `PRIVATE_KEY` from the environment and automatically
reads `<policy-dir>/configs/deployment.toml`. Record:

- `dist/policy_cids.json` (`wasmCid` empty for pure Rego)
- Policy address
- `dist/policy-handoff.json` (fill the
  [handoff manifest](handoff.md); `policyData` stays `[]`)

A client set is several of these deploys. Keep the evaluation order. The
cap is 8. `newton-policy-client` sends them in one `setPolicies` call.

### Published pack

Resolve the policy address with `newton-cli policy packs show --format json`
first ([published-packs.md](published-packs.md)). Never copy it from chat or
GitHub. If the JSON already has a policy address, do not deploy another copy
of that pack. If it has only a legacy `policy_data` address, stop.

On chains other than Ethereum Sepolia (`11155111`), `RPC_URL` must already
be set. Do not invent a public RPC for Base Sepolia (`84532`). Pack lookup
itself needs no RPC.

If `<policy-dir>/secrets_schema.json` exists (or `dist/secrets_schema.json`),
orchestrated CID generation includes it. A secrets schema requires a non-empty
`wasmCid` (`SecretsSchemaWithoutWasm` otherwise). Confirm
`dist/policy_cids.json` after deploy. Pass `--secrets-schema-file <path>`
only to override that default. Do not generate CIDs in a separate
`policy-files generate-cids` step merely because the policy has a secrets
schema.

Useful options:

- `--skip-cids`: reuse existing `dist/policy_cids.json`
- `--secrets-schema-file <path>`: override auto-discovery
- `--pinata-jwt` / `--pinata-gateway`: direct Pinata instead of Newton proxy

## Policy-client integration

Hand off Solidity deploy and wiring to `newton-policy-client`. That skill
uses `forge` / `cast`, not `newton-cli policy-client`.

`registerClient` does **not** create or deploy a client contract. It
registers an existing contract that implements `INewtonPolicyClient`.

`setPolicies` is owner-only on the PolicyClient (`getOwner()`). After
`newton-policy-client` transfers ownership to the login wallet, the local
`PRIVATE_KEY` can no longer send that call, and this skill cannot sign as
the dashboard Turnkey / MetaMask wallet. The login wallet can replace the
set on the same client. Do not deploy a new client for a param or membership
change.

Register only when needed, and only while the local key is still
`getOwner()` (before `setPolicyClientOwner`):

```bash
cast send 0xREGISTRY "registerClient(address)" 0xPOLICY_CLIENT \
  --rpc-url "$RPC_URL" --private-key "$PRIVATE_KEY"
```

Bind the ordered set while the local key still owns the client. One policy
is a one-element array. Two policies:

```bash
PARAMS_0=$(cast from-utf8 "$(cat "$POLICY_DIR_0/configs/params.json")")
PARAMS_1=$(cast from-utf8 "$(cat "$POLICY_DIR_1/configs/params.json")")
cast send 0xPOLICY_CLIENT \
  'setPolicies((address,(bytes,uint32))[])' \
  "[($POLICY_0,($PARAMS_0,<blocks>)),($POLICY_1,($PARAMS_1,<blocks>))]" \
  --rpc-url "$RPC_URL" --private-key "$PRIVATE_KEY"
```

Ask for `<blocks>` if the user has not supplied an expiration policy. Each
`expireAfter` must be greater than 0. Pass the whole set on every
replacement, including unchanged entries. Do not sort.

Registry `setClientOwner` changes the **registry record** owner, not
PolicyClient `getOwner()`. Secrets, `setPolicies`, `setPolicyClientOwner`,
and gateway evaluate all check `getOwner()`. The two owners can diverge if
you transfer one and not the other; they are not substitutes. Contract
ownership is `setPolicyClientOwner` in `newton-policy-client`. If the client
is registered, also update the registry record so it matches.

The integration relationship is:

```text
Application / PolicyClient
  → ordered policy set (1–8)
      → each Policy: Rego + optional wasmCid + its own params
```

A task freezes that set (`policyId`, `policyRevision`, `policies`, one
`wasmArgs` entry per policy). The set allows only when every policy allows.
Replacing the set bumps the revision and invalidates older attestations.

## Upload secrets

Only after:

- The Policy has the intended `secretsSchemaCid` (and a non-empty `wasmCid`)
- PolicyClient address is known
- `getOwner()` on that client is the `newton-cli login` wallet (not the
  local deploy key)
- Secrets JSON matches `secrets_schema.json`
- An RpcWrite gateway API key is available

The gateway authorizes `secrets upload` by matching the API key's dashboard
identity to `getOwner()`. If owner is still the local key, stop and finish
`setPolicyClientOwner(loginWallet)` in `newton-policy-client` first.

Secrets are encrypted client-side and scoped to `(policy client, policy)`.
The installed CLI still names the policy argument `--policy-data-address`.
Pass the **NewtonPolicy** address (the contract that holds `wasmCid`), not a
pre-0.7 PolicyData contract. Run the command once per policy in the set
whose WASM calls `getSecrets()`.

Create `secrets.json` outside tracked source or ensure it is ignored. Then:

```bash
newton-cli --chain-id $CHAIN_ID secrets upload \
  --secrets-file secrets.json \
  --policy-client 0xPOLICY_CLIENT \
  --policy-data-address 0xPOLICY \
  --api-key $API_KEY
```

The gateway validates decrypted JSON against the on-chain schema before
storage. Never show secrets file contents, echo the API key, or commit
either. A later `setPolicies` that keeps the same policy address does not
by itself require a new upload.

## Optional live evaluate

Only when the user requests a gateway round-trip. Do **not** use
`newton-cli task submit-evaluation-request` or `newton-cli policy-client`.

Sign the intent with EIP-712, then POST `newt_createTask` to the gateway for
that chain. Follow `newton-policy-client`
[evaluate-intent-direct.md](../../newton-policy-client/references/evaluate-intent-direct.md).

## Completion report

Report:

- Chain/environment
- Policy addresses in set order (1–8), each `wasmCid` or pure-Rego
- PolicyClient address, `policyId`, `policyRevision`, `getOwner()` (login
  wallet), and registration state
- Whether params and secrets were configured
- Live evaluate result, only if requested
- That a later change is another `setPolicies` by the current owner on this
  client, which bumps `policyRevision` and invalidates old attestations

If deploy used a one-shot process-environment injection and `~/.newton/.env`
still lacks those variables, tell the user that this shell will not be here
next time and that `~/.newton/.env` is how a later agent finds the same vars
without prompting. Do not write the file for them.

Do not expose credentials.

Deployment is done when:

- Each Policy is deployed (or a published policy address was reused).
- PolicyClient is registered when required, `getPolicySetSnapshot()` matches
  the ordered set, and `getOwner()` is the login wallet.
- Params are inside that `setPolicies` call (before owner transfer, when
  this skill's key is the owner).
- Secrets are uploaded when WASM uses them, once per such policy.
- Addresses and the full `setPolicies` tuple are recorded as the later
  update path. Do not record `setPolicy` or `setPolicyAddress`.
- Each `dist/policy-handoff.json` has `policy` filled and `policyData` left
  `[]`.
