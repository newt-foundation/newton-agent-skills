# Deploy, secrets, and live evaluate reference

Use only after local allow/deny simulation passes and the user explicitly asks
to deploy or run live evaluation.

## Disclose early; collect at the deployment checkpoint

When live deployment is requested, state at the beginning that deployment will
eventually need:

- `CHAIN_ID`
- `RPC_URL`
- A funded signing method (the current CLI commands below use `PRIVATE_KEY`)
- An IPFS route:
  - Newton proxy: default; no Pinata credentials
  - Direct Pinata: both `PINATA_JWT` and `PINATA_GATEWAY`

Also name where those secrets should live: the process environment or
`~/.newton/.env` (the durable location both the CLI and this skill load). Do
not ask for values, do not create or populate `~/.newton/.env` for the user,
and do not tell them to do this at install, `doctor`, login, or scaffold.

Do not ask the user to provide these values in chat and do not require them for
scaffold/build/local simulation. Continue through local allow/deny validation.

After local simulation passes and before the first upload or transaction:

1. Read `<policy-dir>/configs/deployment.toml`, generated by `policy scaffold`,
   for non-secret defaults such as chain ID and PolicyData expiration. Read
   `<policy-dir>/.env.example` only as a checklist of supported variables.
2. Reuse values already available from explicit user input, the real process
   environment, or `~/.newton/.env`. Do not search other files.
3. Identify only the missing requirements. Verify secret-bearing environment
   variables by presence without printing their values.
4. If `PRIVATE_KEY`, credential-bearing `RPC_URL`, or (when using direct
   Pinata) `PINATA_JWT` / `PINATA_GATEWAY` are missing from both the process
   environment and `~/.newton/.env`, **stop**. Ask the user to inject them
   outside chat into the process environment or `~/.newton/.env`. Resume only
   after a presence check succeeds.
5. Ask for non-secret choices such as chain/environment and IPFS route when
   they cannot be inferred.
6. Summarize the target chain, planned uploads, and transactions, then obtain
   explicit deployment confirmation.

Do not source or read:

- A project-local `.env` (including the policy directory)
- A `.env` beside a user-specified `newton-cli` binary
- Another repo checkout
- Shell rc files (`~/.zshrc`, `~/.zprofile`, and similar)

A custom CLI path does not change this lookup. An empty `~/.newton/.env` is
missing credentials, not a source to use.

Never invent values. Do not print or commit credentials. Login/API-key setup is
required for gateway operations such as secrets/live evaluate, but not inherently
for scaffold/build/local simulation or Newton-proxy IPFS upload.

Policy lifecycle commands do not require the legacy full
`~/.newton/newton-cli.toml`. With `-p <policy-dir>`, `policy deploy`
automatically reads `configs/deployment.toml`; CLI/environment values override
the file. Use `--deployment-config <path>` only when selecting another
non-secret profile.

Policy-client wiring has additional just-in-time inputs:

- PolicyClientRegistry address
- Existing policy-client contract address
- Expiration values

The application contract must already implement `INewtonPolicyClient`. This
skill wires an existing client; it does not implement or deploy the user's
application contract. Use `newton-policy-client` to create that contract,
bind attested intents, deploy the client with the local key, `setPolicy`,
and transfer `setPolicyClientOwner` to the `newton-cli login` wallet before
secrets.

## End-to-end order

```text
build
  → generate CIDs (+ secrets schema when needed)
  → deploy PolicyData (WASM)
  → deploy Policy (Rego) bound to PolicyData
  → newton-policy-client: deploy / setPolicy / register / setPolicyClientOwner(login wallet) via cast
  → upload secrets when used (requires getOwner() == login wallet)
  → optional live evaluate (EIP-712 sign + gateway newt_createTask)
```

## Orchestrated single-pack deploy

```bash
newton-cli policy deploy -p <policy-dir>
```

This generates CIDs, deploys one PolicyData, and deploys the Policy bound to
that PolicyData. It resolves `RPC_URL` and `PRIVATE_KEY` from the environment
and automatically reads `<policy-dir>/configs/deployment.toml`. Record:

- `dist/policy_cids.json`
- PolicyData address
- Policy address
- `dist/policy-handoff.json` (fill the
  [handoff manifest](handoff.md); this is the input to `newton-policy-client`)

If `<policy-dir>/secrets_schema.json` exists (or `dist/secrets_schema.json`),
orchestrated CID generation includes it. Confirm `dist/policy_cids.json` has a
non-empty `secretsSchemaCid` after deploy. Pass `--secrets-schema-file <path>`
only to override that default. Do not generate CIDs in a separate
`policy-files generate-cids` step merely because the policy has a secrets
schema.

Useful options:

- `--skip-cids`: reuse existing `dist/policy_cids.json`
- `--skip-data --policy-data-address 0x…`: reuse PolicyData
- Repeat `--policy-data-address` for a composite Policy
- `--secrets-schema-file <path>`: override auto-discovery
- `--pinata-jwt` / `--pinata-gateway`: direct Pinata instead of Newton proxy

For composites, preserve PolicyData address order; validation is positional.

## Policy-client integration

Hand off Solidity deploy and wiring to `newton-policy-client`. That skill
uses `forge` / `cast`, not `newton-cli policy-client`.

`registerClient` does **not** create or deploy a client contract. It
registers an existing contract that implements `INewtonPolicyClient`.

`setPolicyAddress` / `setPolicy` are owner-only on the PolicyClient
contract (`getOwner()`). After `newton-policy-client` transfers ownership to
the login wallet, the local `PRIVATE_KEY` can no longer send those calls, and
this skill cannot sign as the dashboard Turnkey / MetaMask wallet.

If params or the Policy address need to change, do **not** `setPolicy` on the
old client. Hand off to `newton-policy-client` to deploy a new client, bind
it, register it, transfer owner, then re-upload secrets here against the new
address. Update any app / SDK / identity link that stored the old client
address. See `newton-policy-client`
[deployment-and-wiring.md](../../newton-policy-client/references/deployment-and-wiring.md).

Register only when needed, and only while the local key is still
`getOwner()` (before `setPolicyClientOwner`):

```bash
cast send 0xREGISTRY "registerClient(address)" 0xPOLICY_CLIENT \
  --rpc-url "$RPC_URL" --private-key "$PRIVATE_KEY"
```

Bind the deployed Policy (same constraint: local key must still own the
client):

```bash
cast send 0xPOLICY_CLIENT "setPolicyAddress(address)" 0xPOLICY \
  --rpc-url "$RPC_URL" --private-key "$PRIVATE_KEY"
```

If Rego uses `data.params.*`, set runtime params:

```bash
PARAMS=$(cast --from-utf8 "$(cat "$POLICY_DIR/configs/params.json")")
cast send 0xPOLICY_CLIENT "setPolicy((bytes,uint32))" "($PARAMS, <blocks>)" \
  --rpc-url "$RPC_URL" --private-key "$PRIVATE_KEY"
```

Ask for `<blocks>` if the user has not supplied an expiration policy.

Registry `setClientOwner` changes the **registry record** owner, not
PolicyClient `getOwner()`. Secrets, `setPolicy`, `setPolicyClientOwner`, and
gateway evaluate all check `getOwner()`. The two owners can diverge if you
transfer one and not the other; they are not substitutes. Contract ownership
is `setPolicyClientOwner` in `newton-policy-client`. If the client is
registered, also update the registry record so it matches.

The integration relationship is:

```text
Application / PolicyClient
  → current Policy address
      → one or more PolicyData addresses
          → WASM + optional secrets schema
```

Tasks refer to the PolicyClient; the protocol resolves its current Policy,
PolicyData, params, and client-scoped secrets.

## Upload secrets

Only after:

- PolicyData has the intended `secretsSchemaCid`
- PolicyClient address is known
- `getOwner()` on that client is the `newton-cli login` wallet (not the
  local deploy key)
- Secrets JSON matches `secrets_schema.json`
- An RpcWrite gateway API key is available

The gateway authorizes `secrets upload` by matching the API key's dashboard
identity to `getOwner()`. If owner is still the local key, stop and finish
`setPolicyClientOwner(loginWallet)` in `newton-policy-client` first.

Secrets are encrypted client-side and scoped to
`(policy_client, policy_data)`. Replacing the PolicyClient (the
`newton-policy-client` workaround when params/policy must change) requires a
new upload to the new client address. Replacing PolicyData also requires a
new upload.

Create `secrets.json` outside tracked source or ensure it is ignored. Then:

```bash
newton-cli --chain-id $CHAIN_ID secrets upload \
  --secrets-file secrets.json \
  --policy-client 0xPOLICY_CLIENT \
  --policy-data-address 0xPOLICY_DATA \
  --api-key $API_KEY
```

The gateway validates decrypted JSON against the on-chain schema before
storage. Never show secrets file contents, echo the API key, or commit
either.

## Optional live evaluate

Only when the user requests a gateway round-trip. Do **not** use
`newton-cli task submit-evaluation-request` or `newton-cli policy-client`.

Sign the intent with EIP-712, then POST `newt_createTask` to the gateway for
that chain. Follow `newton-policy-client`
[evaluate-intent-direct.md](../../newton-policy-client/references/evaluate-intent-direct.md).

## Completion report

Report:

- Chain/environment
- PolicyData address(es) and ordering
- Policy address
- PolicyClient address, `getOwner()` (login wallet), and registration state
- Whether params and secrets were configured
- Live evaluate result, only if requested
- That later param/policy changes need a new PolicyClient, not `setPolicy` on
  this one after owner transfer

If deploy used a one-shot process-environment injection and `~/.newton/.env`
still lacks those variables, tell the user that this shell will not be here
next time and that `~/.newton/.env` is how a later agent finds the same vars
without prompting. Do not write the file for them.

Do not expose credentials.

Deployment is done when:

- PolicyData and Policy are deployed/bound.
- PolicyClient is registered when required, points to the Policy, and
  `getOwner()` is the login wallet.
- Params are set when Rego uses them (before owner transfer).
- Secrets are uploaded when WASM uses them.
- Addresses and rerun/update commands are recorded. Do not record
  `setPolicy` against this client as a later mutation path.
- `dist/policy-handoff.json` is complete (`policy` and `policyData` filled).
